Technical overview

Pi Sandbox

Managed AI-agent access for development and production servers.

Developers, operations staff, and administrators may need an AI agent to review or edit configuration, troubleshoot logs, work with source code, run commands, or call internal services. The goal is to provide that access through centrally managed tools, permissions, and human approvals instead of giving the model an uncontrolled shell.

Users

Run an interactive agent in a chosen working directory and see proposed operations before they run.

Administrators

Define available tools, approval requirements, execution mode, network access, and user exceptions.

Security and operations

Deploy one consistent, fail-closed policy across managed development and production systems.

PurposeAttended, policy-controlled agent use

Terminology and components

What Pi Sandbox manages

AI agent An interactive application that sends a user request to a language model and can carry out model-requested operations on the host.
Pi The terminal application: it provides the conversation UI, contacts the configured language model, and maintains sessions and user state.
Tool A named operation with structured input, such as read, edit, bash, or git_clone. The model can request only tools it is shown.
Pi Sandbox A managed distribution of Pi that replaces its executable tools with policy-controlled implementations and administrator-selected extensions.
Division of responsibility Pi handles the interactive agent experience. Pi Sandbox governs which operations are exposed, whether they require approval, and where approved work executes.
TerminologyAgent interface plus managed execution

Request and approval flow

How an agent operation reaches the server

01 User request

The user asks Pi to inspect, troubleshoot, or change something from the current host working directory.

→
02 Model response

The configured language model may answer directly or request one advertised tool.

→
03 Structured tool call

Pi Sandbox validates the tool name and its typed arguments.

→
04 Policy and approval

The effective per-tool policy allows, prompts, refuses, or hides the operation.

→
05 Execution and result

The exact approved request runs through its fixed boundary; output returns to Pi.

Tool exposure is independent Model-visible Bash can be disabled while selected typed tools remain available. The user's explicit ! shell command is human-only and follows the configured execution backend.

Administrative policy

What administrators configure

distribution.toml · build time

Installed capabilities

Determines which extension implementations can exist in the package, installation paths, and the Linux Bubblewrap provider.

config.toml + models.json · global

System baseline

Defines active extensions, every tool policy, model catalog, scoped environment, execution backend, and network mode.

users.d + groups.d · optional

Per-user exception

A root-owned Linux drop-in may override selected environment, model, execution, network, and tool-policy values for matching users and groups.

allowRun without a model-tool prompt.
askRequire interactive approval.
denyAdvertise the tool but refuse calls.
disabledDo not show the tool to the model.
AdministrationStrict, versioned, root-managed inputs

Execution boundaries

Where approved operations run

Path Typical operations Authority and containment Policy controls that remain
Bubblewrap
Linux		 Built-in file, search, edit, and shell tools Host filesystem read-only; launch directory configured read/write or read-only at the same path; private runtime and optional isolated network. Tool visibility, approval, fixed request mapping, time/output limits, and descendant cleanup.
Direct
Linux / macOS		 The same built-ins when containment is not selected Runs as the invoking user with ordinary host filesystem and network authority. This is not a sandbox. The same tool catalog, policies, approvals, direct argument handling, and process lifecycle controls.
Managed host tool Small typed exceptions such as git_clone Runs outside Bubblewrap as the invoking user because it needs host identity or network access. Fixed executable, bounded structured arguments, extension-specific validation, and the same per-tool approval policy.
Two separate decisions Policy determines whether an operation may run. The selected execution path determines what an allowed operation can reach. Approval never changes the configured boundary.
Execution boundariesNo fallback from Bubblewrap to direct execution

Configuration example

Global policy with an optional user exception

# /etc/pi-sandbox/config.toml — excerpt
config_version = 10
models_file = "/etc/pi-sandbox/models.json"

[codemode]
enabled = false

[mcp.servers]
audit = { enabled = false, facility = "local0" }
filesystem = { cwd_writable = true, hidden_paths = [] }
[sessions]
retention_days = 365
[execution]
backend = "bubblewrap"
[identity]
mode = "broker"
[network]
mode = "none"
[environment.pi]
[environment.sandbox]
[environment.extensions]
[extensions.git]
allowed_hosts = ["github.com", "git.example.com"]
allowed_schemes = ["https", "ssh"]
[tools]
read = { mode = "allow", session_grant = "never", audit = false }
write = { mode = "ask", session_grant = "offer", audit = true }
bash = { mode = "disabled", session_grant = "never", audit = true }
git_clone = { mode = "ask", session_grant = "never", audit = true }
# A complete file also declares grep, find, ls, and edit.
# groups.d/admin.toml — optional
version = 7
group = "admin"

[overrides.tools.git_clone]
mode = "allow"
session_grant = "never"
Effective policy The main TOML supplies defaults. Matching user and group rules combine explicit permissions using least restrictive wins; omitted settings inherit defaults.

Environment is scoped separately for Pi's model connection, sandboxed commands, and individual managed extensions. Environment values cannot enable tools or grant approvals.

Operating scope

Intended use and scope of control

Adds managed controls for agent-requested operations without replacing the user's existing access to the server.

Intended use

  • Configuration review and editing, log troubleshooting, diagnostics, repository work, and coding on development or production servers.
  • A consistent administrator-defined tool set instead of per-user agent configuration.
  • Typed tools with model-visible Bash disabled when a narrower interface is preferred.
  • A distributable public core with separately compiled private extensions.

Scope of control

  • Existing Unix account permissions and server security controls remain authoritative.
  • Users retain whatever access to software, files, and services their account and organizational policies already permit.
  • Administrators control agent tools independently: each may be hidden, denied, forced through interactive approval, or allowed.
  • Bubblewrap adds execution isolation through filesystem mount controls, private process and runtime namespaces, bounded writable locations, and administrator-selected network isolation.
